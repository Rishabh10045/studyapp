    Real-world examples

    Stack Overflow: scaling up goes far
    Has publicly described serving its very large traffic from a small number of powerful web and SQL Server machines: proof that vertical scaling plus good caching can last a long time.
    Facebook: caching at massive scale
    The paper 'Scaling Memcache at Facebook' (NSDI 2013) describes a huge Memcached tier that absorbs reads in front of MySQL.
    Instagram: sharding PostgreSQL
    Its 2012 engineering post 'Sharding & IDs at Instagram' describes many logical shards mapped onto fewer physical PostgreSQL servers, with IDs that embed the shard.
    Netflix: stateless services that expect failure
    Runs stateless services on AWS with autoscaling, and built Chaos Monkey to randomly terminate instances so every service must survive losing one.

    Common interview pitfalls

    • Jumping to sharding or microservices before estimating the load
    • Saying 'add more servers' while sessions still live in server memory
    • Forgetting that the load balancer itself needs redundancy
    • Scaling the app tier and ignoring that the database becomes the bottleneck
    • Adding a cache without a TTL or invalidation story
    • Sending reads to replicas without mentioning replication lag
    • Naming components without saying the trade-off each one brings

    Interview practice

    QuestionYour photo-sharing startup runs its API and PostgreSQL on one server. Traffic is expected to grow 50x over the next year, and about 95% of requests are reads. How would you evolve the architecture? Answer out loud first, then reveal the model answer.
    1. Clarify and estimate
      Ask for current DAU, peak QPS and data growth; 50x growth and 95% reads tells you reads are the main pressure.
    2. Scale up and separate the DB
      Quick win: move PostgreSQL to its own, larger machine; add indexes for slow queries.
    3. Make the app stateless
      Sessions to Redis or tokens; uploaded photos to object storage (e.g. S3) instead of local disk.
    4. Load balancer + multiple app servers
      Redundant LB, autoscaled app servers across availability zones, health checks.
    5. CDN and cache
      Serve photos via a CDN; cache hot metadata (profiles, feeds) with cache-aside and TTLs.
    6. Read replicas
      Route reads to replicas, writes to the primary; handle lag with read-your-writes; set up automatic failover.
    7. Plan for sharding, but don't start there
      Choose a likely shard key (user_id) and shard only if write volume or data size outgrows one primary.
    8. Close with trade-offs and monitoring
      Name the remaining SPOFs, stale-cache and replica-lag trade-offs, and the metrics you'd watch (p99 latency, DB CPU, cache hit ratio).

    Recap card

    1. Scale up first for simplicity; scale out when you hit the ceiling or need redundancy.
    2. Horizontal scaling needs stateless servers behind a redundant load balancer.
    3. Then the database is the bottleneck: indexes, cache, read replicas, in that order.
    4. Shard only when writes or data size outgrow one primary; it brings real costs.
    5. Every fix moves the bottleneck: name it, remove SPOFs, and state the trade-off.
